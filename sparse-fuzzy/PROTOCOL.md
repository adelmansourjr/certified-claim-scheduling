# Exact sparse character matching with a fixed evidence verifier

## Hypothesis

The original frozen verifier always performs its character matching block even with the existing score certificate. For each retrieval shortlist, character similarity needs to visit only words that share a character trigram with the claim word. A second optimization reuses exact term-pair similarities across subclaims in the same evidence document. With exact arithmetic on intersection cardinalities and the original float aggregation order, the fast scorer must preserve every atom's six character features and every compound claim verdict.

## Assessment

Use the prior pinned WiCE train, development and test datasets. Select the original fitted verifier by its existing development routine, then freeze its weights, intercept, decision threshold, parent order and block order. The same conjunction and labels as the old evaluator apply. No support line annotations or verdict labels go into inference. The reused held-out WiCE test changes the performance question and algorithms, with no claim of independent data replication. After development, lock source, inputs and frozen model files before the first new test timing. Select policy hyperparameters, if any, on development only.

Methods:
- **Prior certificate** unchanged, including exact parent ordering, stage-level early exits and its established cache.
- **Cached dense certificate** uses exactly the same control flow and character features, caches term-pair Jaccard within a document, and filters pairs when their lengths prohibit any improvement.
- **Sparse certificate** uses the same decision model, ordered score certificate and term-pair cache. An inverted index over evidence words maps query grams to candidate word positions. Within each selected line, absent terms with no indexed gram intersection have score zero. A document-local cache reuses the Jaccard result; length bounds can rule out improvements. Index creation, filtering and routing are charged. Consider selection-dependent construction or reuse of the index, chosen before test; all variants give exactly the same scores.
- **Sparse exact eager** ablation evaluates all feature blocks for the same first-failure parent policy. This isolates what stage certificates contribute after improving the character block. Compare three candidate representations of the index on development: ordinary word postings sets, packed positions with lossless bit unions, and a 1,024-bit trigram signature prefilter with exact fallback. Only disjoint signatures prune a word, so a collision cannot remove a valid candidate. Lock the fastest certified variant; keep all variants in the reporting table.

Report end-to-end CPU, charged preprocessing and query scoring. For 5 interleaved seeded repeats per case, report the ratio of sums of median process CPU times, plus a bootstrap over the prior connected document groups. Initial development selects the strongest prior or cached-dense comparator by the same aggregation; the primary margin is at least 15% lower aggregate CPU with a lower paired 95% bound greater than 5%, preserving all scores and decisions. The 5% lower bound is a practical effect threshold for this implementation and machine. Character matching cache state cannot flow between inputs or timed policies; a warmed process may retain the same bounded term-to-grams cache as the prior code. Instrument separately for amount of character matching work, explicitly listing cache misses/paths so they do not substitute for latency metrics. Keep the original feature-set quality metrics unchanged because this tests exact inference and makes no claim of quality gains, portability of specific timing, or acceleration of an LLM.
